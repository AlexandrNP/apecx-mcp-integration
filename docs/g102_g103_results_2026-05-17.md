# G102 + G103 — empirical results & honest analysis

**Date**: 2026-05-17
**Methodology**: MBPP N=100 against mistral-nemo:latest, same harness + sandbox as the G96 baseline. Result JSONs at `tests/benchmarks/results/g102_g103_*.json`.

## TL;DR

| Codegen | N | Pass@1 | Wall/problem | Cost mult | Δ vs direct |
|---|---|---|---|---|---|
| direct (G96 baseline) | 100 | **0.650** | 3.0 s | 1.00× | — |
| tdr (G96 baseline) | 100 | 0.680 | 9.3 s | 3.05× | +3pp at 3× cost |
| hd_rss (G96 baseline) | 100 | 0.500 | 3.3 s | 1.09× | -15pp |
| **best_of_n (G103, NEW)** | 100 | **0.750** | 4.2 s | 1.38× | **+10pp at 1.4× cost** |

**best_of_n is the new MBPP leader against mistral-nemo** — and at much better cost-efficiency than TDR (+10pp at 1.4× cost vs TDR's +3pp at 3× cost).

## G103 best_of_n — the real win

**Mechanism**: 3 independent samples at temperature=0.4; run each against test_code; return the first that passes (or last if none pass).

**Why it works on MBPP**:
* MBPP problems are atomic — single-function tasks. The LLM occasionally gets them wrong by noise; a second/third sample with diversity has a fresh chance.
* The "first sample passes" common case keeps cost low (4.2 s avg vs 3.0 s direct = ~1.4× cost, NOT 3× as worst-case math would suggest).
* The execution oracle (run vs test_code) gives best_of_n a clean signal — first sample that passes wins, no LLM-judged ranking ambiguity.

**Per-problem transitions vs direct**:
* **12 unique fixes** (direct failed → best_of_n passed)
* **2 unique breaks** (direct passed → best_of_n failed; LLM at temp=0.4 happened to be worse than temp=0 on those specific problems)
* Net: +10 problems passed = +10pp absolute lift

**Failure histogram on the remaining 25 failures**:
* 22 AssertionError (logic bugs no sample correctly solved — independence doesn't help when ALL samples make the same mistake systematically)
* 2 TypeError (occasional argument-type wrongness)
* 1 NameError (rare entry-point naming noise)

The clean failure profile suggests the remaining gap (25/100) is **systematic LLM blindspots** — problems where mistral-nemo's reasoning is wrong in a CONSISTENT way that diversity can't dodge. The next pattern targeting these would need execution feedback (TDR's mechanism) or external context (RAG-grounded).

## G102 + G102b hd_rss_v2 — modest gain, honest accounting

**G102 mechanism**: templated composer (deterministic helper concat + LLM-written orchestrator only).

**G102b mechanism**: AST-based post-hoc entry-point rename in `_atomic_codegen` + both composers.

**Empirical sequence**:
1. G102 standalone N=100: 50/100 = 0.500 — **IDENTICAL to original hd_rss**. Hypothesis disproved.
2. Inspection of failing samples surfaced the actual root cause: the LLM normalizes function names to lowercase snake_case in `_atomic_codegen`, regardless of the requested entry_point. The 17 MBPP NameErrors came from atomic-codegen NOT from `_compose`.
3. G102b adds the AST rename. N=100 re-run: 53/100 = 0.530 (+3pp, NameErrors 17→9).

**The remaining gap vs direct (53 vs 65)**: HD-RSS's `_judge_atomic` LLM call adds noise — sometimes judges simple problems "composite" → decomposes → composition introduces logical errors. Decomposition is the WRONG strategy for MBPP. Even with perfect composition, HD-RSS would still pay the atomicity-judgment overhead.

**Honest assessment**: hd_rss / hd_rss_v2 are not useful patterns for atomic-problem datasets. They might still help on compositional datasets (SciCode's multi-step physics computations), but the G96 SciCode result was already 0pp delta — composition is not the bottleneck there either. **Recommendation**: don't run HD-RSS in production benchmark sweeps; keep it in the codebase as a reference for when an LLM-driven decomposer + a deterministic composer + a strong orchestrator-judgment heuristic come together (none of which mistral-nemo provides today).

direct is still the most cost-efficient for raw pass rate, but **best_of_n is dramatically better quality-per-cost than TDR** (+10pp vs +3pp at less than half the cost mult). TDR's revision loop is paying for diminishing returns on MBPP.

## What this teaches about pattern selection

Re-validates the G101-derived rule "**TDR's marginal value scales inversely with the baseline**" with a complementary finding:

* On **MBPP** (in-distribution; baseline 0.65): **best_of_n > tdr > direct**. The LLM is mostly right; sampling diversity catches its rare mistakes more efficiently than iterative revision.
* On **SciCode** (compositional; baseline 0.19): **tdr > direct = hd_rss**. Execution feedback teaches the LLM something diversity alone can't.
* On **nbnative** (out-of-distribution; baseline 0.10): **tdr >> direct, hd_rss**. Execution feedback is the only mechanism that gives the LLM a signal it doesn't already have from training.

best_of_n is predicted to help LESS on SciCode + nbnative because those failure modes are systematic (LLM doesn't know the right API at all — N samples all wrong in the same way). Verification via SciCode + nbnative benchmarks is the next chain step.
