# G99 — TDR as a framework-native YAML workflow

**Date**: 2026-05-17
**Status**: ✅ Shipped (workflow YAML + iteration step + integration test + four nanobrain framework fixes + lightweight WorkflowBuilder variant)
**Related**: G18 (LoopController + cycle validator); G93 (Python TDR codegen); G96 (large-N benchmark sweep); G98 (HD-RSS); G101 (failure-mode taxonomy)

## TL;DR

* TDR (Test-Driven Recursive Refinement) is now expressible as a pure-YAML nanobrain workflow with cycle detection ENABLED (`allow_cycles: false`). The cycle is permitted because every cycle passes through a `LoopController` — the G18 Step 2 validator extension.
* The workflow uses **one custom step** (`TdrIterationStep`) + one framework primitive (`LoopController`) + four `ConditionalLink`s + one `DirectLink`. The cycle topology is `tdr_iter → loop_gate → tdr_iter` (back-edge through the LoopController).
* End-to-end verification against Ollama mistral-nemo surfaced **four real silent-failure bugs in nanobrain itself**, all fixed in this chain:
  1. `WorkflowGraph._get_cycles_info` was missing — `validate_graph`'s G18 success branch crashed silently, turning success into false validation failure.
  2. `ConditionalLink._init_from_config` didn't set `self.auto_transfer` — every ConditionalLink silently no-op'd.
  3. `ConditionalLink.transfer` (condition-met branch) lacked a `target.set(data)` fallback for data-unit targets — transferred nothing to workflow-level outputs.
  4. `LoopController.process` didn't unwrap the trigger envelope — back-edge payload was doubly-wrapped.
* All four bugs would have hit ANY cycle-bearing workflow with ConditionalLinks in production. Found because end-to-end testing exercises code paths the per-class unit tests don't.

Cycle: `tdr_iter → (ConditionalLink, !exec_succeeded) → loop_gate → (ConditionalLink, allow_continue) → tdr_iter`. The `_all_cycles_pass_through_loop_controller` validator extension (G18 Step 2) allows this back-edge because `loop_gate` is a LoopController.

## Why this design (one TdrIterationStep + cycle primitives)

Two designs were considered:

**Design A** — 5 adapter Steps (envelope-to-writer-input,
writer-output-to-envelope, envelope-to-exec-input, exec-output-to-envelope, exec-output-to-critique) gluing existing CodeWriteStep + IsolatedPyExecStep with DirectLinks.

**Design B** (chosen) — one custom `TdrIterationStep` that internally composes CodeWriteStep + IsolatedPyExecStep via `from_config` and `.process()` calls. The framework cycle primitives (LoopController + ConditionalLink) drive the iteration; the per-call mechanics are inside one Step.

Design B chosen because:
1. The framework demonstration here IS the cycle topology — DirectLink, ConditionalLink predicate branching, back-edge through LoopController, validator allowance. The per-iteration LLM+exec is the payload of the cycle, not what the cycle is proving.
2. Design A would have 12 step entries + 15 link entries in the YAML, dominated by dict-reshaping adapters whose only purpose is satisfying the closed-class rule. Less readable; not more framework-native; more lines to maintain.
3. Step composition (Step containing Step via from_config + .process() calls) is a legit framework pattern — `SubworkflowStep` is the canonical example.
4. The cycle-driven iteration mechanism IS being driven by framework primitives. The LLM+exec packaging is orthogonal.

## Nanobrain framework fixes shipped in this chain

All four fixes ship with regression tests at
`nanobrain/tests/unit/test_g99_framework_fixes_2026_05_17.py` (15 tests). Net: 15 new + 164 pre-existing link/trigger/cycle tests pass; **0 regressions**.

### Fix 1 — `WorkflowGraph._get_cycles_info()` was missing

The G18 Step 2 success branch in `validate_graph` referenced `self._get_cycles_info()` for its log statement. The method didn't exist. The resulting `AttributeError` was caught by `handle_error` which logged a warning and returned `(False, ["Graph validation failed"])`. Net: every cycle-bearing workflow with LoopController bounding LOADED via `from_config` but REFUSED to run via `.run()`. The smoke tests passed (they only load); the integration test exposed it.

Added the method to return a human-readable description of detected cycles (`['a -> b -> c -> a']` shape).

### Fix 2 — `ConditionalLink._init_from_config` missed `self.auto_transfer`

`extract_component_config` pulled `auto_transfer` from the config; `_init_from_config` never assigned it to `self`. The base class's `_setup_automatic_transfer_if_possible` reads via `getattr(self, 'auto_transfer', False)` — so every ConditionalLink silently treated as a no-op link. Visible only when an integration test exercised the auto-transfer path; unit tests that called `.transfer()` directly bypassed this.

Added one line: `self.auto_transfer = component_config.get('auto_transfer', True)`.

### Fix 3 — `ConditionalLink.transfer` (condition-met branch) lacked data-unit fallback

The condition-met branch tried `target.input_data_units[0]` (step's input data unit list) OR `target.set_input()`. Workflow-level output data units and step input data units accessed directly by name don't have either attribute — they have `.set()`. So when the condition matched and target was a data unit, the transfer silently no-op'd.

The `gate_to_bottom` branch (condition-NOT-met case) already had the `await self.target.set(sentinel)` fallback. Fix: added the parallel `await self.target.set(data)` fallback to the condition-met branch.

### Fix 4 — `LoopController.process` didn't unwrap trigger envelope

When invoked via the data-driven cascade, the framework delivers `{<input_data_unit_name>: <actual payload>}` to the Step's process. CodeWriteStep + IsolatedPyExecStep both explicitly unwrap. LoopController did not — it passed the wrapper dict through under `payload`. Downstream steps consuming the controller's output via a back-edge received doubly-wrapped data they couldn't decode.

Added the same conservative unwrap pattern: when input is a single-key dict whose key matches one of the controller's input data unit names AND whose value is a dict, unwrap.

## Cost vs Python TDR

The framework-native workflow has slightly higher wall time than the Python TDR codegen due to:
- Per-iteration trigger evaluation overhead (~200ms per cycle iteration)
- ConditionalLink predicate evaluation on every source data unit change (~10ms × 2 per iter)
- LoopController invocation overhead (~100ms per iter)

On mistral-nemo where each iteration is 60-150s of LLM time, this overhead is <1%. On a 10× faster model (Sonnet, Llama-3-70B on GPU), the overhead becomes noticeable but is still <5%. For benchmark use the wall difference is in the noise.

## What this enables that the Python TDR didn't

* **Cycle-bearing workflows can now be composed via SubworkflowStep.** The TDR refine loop can be embedded as one step of a larger workflow (e.g., "if the synthesizer's draft fails its validation gate, run it through TDR refine"). The Python TDR couldn't be composed that way without writing wrapper code.
* **Operators can tune iteration cap via YAML.** Bump `max_iterations` in `steps/loop_gate.yml` without touching code; the change applies to both YAML and lightweight builds.
* **Reference for future cycle-bearing patterns.** Future patterns like "validator-driven repair loop" or "best-of-N revision with structural consensus" can use this workflow as the structural template — copy the topology, swap TdrIterationStep for the new iteration body.
